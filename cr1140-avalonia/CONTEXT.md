# Context: cr1140-avalonia

## Responsibility

A **.NET class library** (`Cr1140.Avalonia`) providing **CR1140/CR1141/CR1102 Avalonia LinuxFramebuffer support**: (1) a custom **input backend** for keypad-only embedded panels — thin, typed wrapper over Linux evdev that maps the CR1140/CR1141/CR1102 gpio-keys device (`/dev/input/event1`) to a managed `KeypadKey` enum and raises `KeyPressed`/`KeyReleased` plus derived gesture events (`KeyTapped`, `KeyDoubleTapped`, `KeyHeld`, `KeyHolding`) for application-driven navigation; (2) a **`SoftKeyFooter` control** — a 6-key soft-key footer with two layout modes (Physical and Natural) for operator-panel UIs; (3) a **`SystemTelemetry`** collector plus **`DeviceInfo`** — a readable, framework-agnostic system-telemetry API (CPU, memory, SoC/board temperature, uptime, load) and device/network state; (4) **two software output backends** with display rotation — `RotatingFbdevOutput` (fbdev) and the tear-free `RotatingDrmOutput` (DRM/KMS DUMB double-buffer + page-flip) — mount the panel in any orientation; (5) onboard-LED control (`LedSysfs`/`LedMode`/`LedDriver` over `/sys/class/leds`: RGB status light + RGB keypad-button backlight with animation modes; mirrors the Rust HAL `sys` LEDs + SDK `led`); (6) a **device-profile abstraction** (`DeviceProfile` / `DeviceProfiles`) — single source of truth for per-device constants (panel size, touch/keypad, function-key/nav presence, keypad device path, backlight node + max hint, SoC thermal zone, LED flags) enabling CR1102 (10" 1280×800 touchscreen) support alongside the original CR1140/CR1141 (4.3" 800×480 keypad-only). The evdev keycode map is unchanged (shared standard ifm gpio-keys).

**Bounded scope**: CR1140/CR1141/CR1102 Avalonia LinuxFramebuffer support (keypad input + soft-key control + display rotation + device profiles) plus a small, readable system-telemetry API. This is NOT a full device SDK — it solves the gaps a keypad-only panel hits (keypad input, soft-key footer UI, display orientation, and read-only system telemetry) in Avalonia's LinuxFramebuffer platform support. CR1102 support is **additive** (the keypad map stays standard ifm gpio-keys; the output backends are resolution-agnostic and read the panel mode at runtime). Rendering, layout, MVVM, and application logic are the consuming app's responsibility (see `cr1140-avalonia-demo` for a reference implementation). The telemetry API is a deliberate mirror of the Rust `cr1140-sdk` `metrics` + `device` modules, so a .NET app gets the same data out of the box.

Hardware/OS ground truth: [`../docs/device-facts.md`](../docs/device-facts.md) (CR1140/CR1141), [`../docs/device-facts-cr1102.md`](../docs/device-facts-cr1102.md) (CR1102).

## API

**Namespace**: `Cr1140.Avalonia.Input`

| Type | Role |
|------|------|
| `interface IKeypadInput` | Shared managed keypad event surface implemented by both on-device `EvdevKeypadInput` and desktop `WindowKeypadInput`. Six events, each `event Action<KeypadKey>?`: `KeyPressed`, `KeyReleased`, `KeyTapped`, `KeyDoubleTapped`, `KeyHeld`, `KeyHolding`. Consuming an app off this interface (e.g. `MainViewModel(IKeypadInput)`) lets the same view-model run unchanged on the device and in the desktop emulator. |
| `sealed class EvdevKeypadInput : IInputBackend, IDisposable` | Custom Avalonia input backend. Constructors: `EvdevKeypadInput(string devicePath)` (single device, default `/dev/input/event1`) and `EvdevKeypadInput(string devicePath, KeyGestureOptions?)`, `EvdevKeypadInput(IReadOnlyList<string> devicePaths)` (multi-node reading for devices with multiple uinput keypad nodes — CR1102's "PDM3 virtual keyboard" nodes `[live ✓ 2026-09-21]`); static factories `ForDevice(DeviceProfile)` (auto-discovers by `KeypadDeviceName` if present, else uses `KeypadDevicePath`) and `DiscoverByName(string deviceName)` (scans `/dev/input/event*` for matching `EVIOCGNAME`, returns matching paths). Raises, on background threads: `KeyPressed` (key-down, `EV_KEY` value `1`), `KeyReleased` (key-up, value `0`), and the derived gestures `KeyTapped`, `KeyDoubleTapped`, `KeyHeld` (long-press, one-shot), `KeyHolding` (press-and-hold repeat) — all `event Action<KeypadKey>?`. Auto-repeat (value `2`) is ignored; holding is timer-driven. Implements `Initialize(IScreenInfoProvider, Action<RawInputEventArgs>)` (starts the evdev reader thread + a gesture timer) and `SetInputRoot(IInputRoot)`. `Dispose()` stops the reader threads and timer. **Multi-node reading** is thread-safe; each node is polled by its own background thread, events are merged.
| `sealed class KeyGestureDetector` | Pure, allocation-free gesture state machine (no Avalonia dependency, host-testable). Consumes `Down(key, nowMs)`/`Up(key, nowMs)` plus a periodic `Tick(nowMs)` with caller-supplied monotonic milliseconds; raises `Tapped`, `DoubleTapped`, `Held`, `Holding`. Per-key state in a fixed array; `IsIdle` tells the owner when it can stop ticking. **Not** thread-safe — the owner (`EvdevKeypadInput`) serializes access. |
| `sealed class KeyGestureOptions` | Gesture timing (all `TimeSpan`): `HoldThreshold` (default 500 ms), `HoldRepeatInterval` (default 150 ms), `DoubleTapWindow` (default 300 ms). Passed to `KeyGestureDetector` and the `EvdevKeypadInput` gesture ctor. |

| `sealed class CompositeInputBackend : IInputBackend, IDisposable` | Combines Avalonia's stock touch backend (`EvDevBackend`) with the keypad backend (`EvdevKeypadInput`) for touch panels like the CR1102. Pass the touch device path/name (from `DeviceProfile.TouchDevicePath`/`TouchDeviceName`) and the keypad backend; implements `Initialize` by forwarding to both backends and merging their raw events. `Dispose()` disposes both. |
**Namespace**: `Cr1140.Avalonia.Controls`

| Type | Role |
| `enum SoftKeyFooterLayout` | Layout mode for `SoftKeyFooter`: `Physical` (keypad-ordered: F6 F4 F2 · d-pad · F1 F3 F5 for 6-key; F1 F2 F3 F4 · d-pad · F5 F6 F7 F8 for 8-key CR1102) or `Natural` (F1–F6 / F1–F8 left-to-right). |
| `class SoftKeyFooter : Border` | A soft-key footer control. Properties: `Layout` (SoftKeyFooterLayout, default Physical), `Orientation` (`Avalonia.Layout.Orientation`, default `Horizontal`; `Vertical` renders the footer as a **column** for side-mounted keypads — e.g. the CR1102's right-edge keys), `FunctionKeyCount` (int, default 6; set to 8 for CR1102 to render F7/F8 slots), `ShowDPad` (bool, default true; centre d-pad in **both** layouts), `F1`–`F8` (string? per-key labels; F7/F8 only rendered if `FunctionKeyCount == 8`), styling brushes (`DividerBrush`, `KeyForeground`, `LabelForeground`, `DPadForeground`, `DPadBackground`), d-pad text (`DPadLine1`, `DPadLine2`). Derives from `Border`, so `Background`, `BorderBrush`, `BorderThickness` style the footer; the control sets its own `Height` (horizontal) or `Width` (vertical) per `Orientation`. Dark defaults suit an operator panel. |
| `static class SoftKeyLayoutMap` | Single source of truth for the keypad's physical F-key order and the hardware→logical remap. `PhysicalOrderFor(6)` = F6 F4 F2 F1 F3 F5; `PhysicalOrderFor(8)` = F1 F2 F3 F4 F5 F6 F7 F8 (CR1102, sequential `[live ✓ 2026-09-21]`). `NaturalOrderFor(int functionKeyCount)` returns the natural F1–F6/F1–F8 sequence. `ToLogical(KeypadKey, SoftKeyFooterLayout)` (2-arg, 6-key) and `ToLogical(KeypadKey, SoftKeyFooterLayout, int functionKeyCount)` (3-arg, supports 8-key) — identity in Physical; physical-position based in Natural (e.g. hardware F6 → logical F1 in 6-key; on the CR1102 physical == natural, so the 8-key is identity in both modes). Arrow/Enter keys pass through.

**Namespace**: `Cr1140.Avalonia.Telemetry`

| Type | Role |
|------|------|
| `sealed class SystemTelemetry` | Pull-based telemetry collector. Default ctor reads SoC thermal zone `DefaultSocThermalZone` (=0); `SystemTelemetry(uint zone)` overrides it; `SystemTelemetry(uint? zone, IfmSystemTemperatures? ifmTemps = null)` — when `ifmTemps` is supplied (CR1102) SoC=`rCore0` and board=`rBoard` come from `com.ifm.Io.Temperature` D-Bus; otherwise SoC = thermal zone, or (null zone) the ZynqMP sysmon via IIO (`ProcFs.ReadXilinxSysmonTempC()`), and board = `lm75` hwmon `[live ✓ 2026-09-21]`. `Sample()` returns a `TelemetrySnapshot`. Holds one `CpuSampler` internally — reuse the instance; **no threads, no timers** (the app drives the cadence). |
| `readonly struct TelemetrySnapshot` | One point-in-time read: `CpuPercent`, `Memory` (`MemInfo?`), `SocTempC`, `BoardTempC`, `UptimeSeconds`, `Load1` — each independently optional (`double?`), so a missing `/proc` file or thermal zone degrades that field to `null` without failing the sample. |
| `readonly struct MemInfo` | `TotalKb`, `AvailableKb`, and computed `UsedPercent` (0..100). |
| `sealed class CpuSampler` | Standalone busy-% sampler between two `/proc/stat` reads; `Sample()` reads the file, `Update(idle, total)` is the pure delta (host-testable). First call primes → 0%. |
| `static class ProcFs` | Pure parsers (`ParseStat`, `ParseMeminfo`, `MemUsedPercent`, `ParseUptime`, `ParseLoadavg`, `ParseMillidegrees`, `ParseIioTempC`, `FormatUptime`) and thin `/proc` + `/sys/class/thermal` + IIO readers (`ReadMeminfo`, `ReadUptime`, `ReadLoadavg`, `ReadTempC(zone)`, `ReadXilinxSysmonTempC()` — the ZynqMP sysmon SoC temp). Read a single metric yourself, or unit-test the parsers without a filesystem. |
| `static class DeviceInfo` | Device/OS identity + network state: `Hostname()`, `OsRelease(key)` / `OsReleaseValue(content, key)`, `ReadBoardTempC()` (hwmon lm75), `OperState(iface)`, `IPv4(iface)`, `CpuModel()`, `CpuCount()`. |
| `sealed class IfmSystemTemperatures` | Reads the **CR1102's on-board temperatures** over the `com.ifm.Io.Temperature` D-Bus interface (the `ifm_service_io` MCU): `Core0()` (processor core, `rCore0`) and `Board()` (mainboard, `rBoard`), both `int?` in whole °C. The same source CODESYS's `ifmDevice_ecomatDisplay` exposes; the CR1102's ZynqMP has no thermal-zone/hwmon node. Invoked through `gdbus` on the system bus, fail-soft (null off-device). Wired into `SystemTelemetry` when `DeviceProfile.TemperatureViaDbus` is true `[live ✓ 2026-09-21]`. |

The telemetry types are **pure BCL** (no Avalonia dependency) and offered as **data, not a control** — an app reads them and binds/renders as it likes.

**Namespace**: `Cr1140.Avalonia.Output`

| Type | Role |
|------|------|
| `enum DisplayRotation` | Clockwise rotation applied to every frame before it reaches the framebuffer, so the panel can be mounted in any orientation: `None` (0°), `Clockwise90`, `Clockwise180`, `Clockwise270`. Values are the angle in degrees. 90°/270° swap the logical resolution (native 800×480 landscape → 480×800 portrait). |
| `sealed class RotatingDrmOutput : IOutputBackend, IFramebufferPlatformSurface, IDisposable` | The **DRM/KMS** sibling of `RotatingFbdevOutput` — **tear-free**. Opens the DRM primary node (`card` / `/dev/dri/card0` if specified; **null card auto-detects the connected KMS display card** by scanning `/dev/dri/card*` and picking the first card with a connected connector — skips render-only cards like the CR1102's lima GPU card0, selects the ifm_dc display card1 `[live ✓ 2026-09-21]`), becomes DRM master, modesets the first connected connector's preferred mode, allocates **two** XRGB8888 (`Bgra8888`) DUMB scanout buffers, reports a **logical (rotated)** `PixelSize`, has Skia render into a private back buffer, then each frame rotate-blits (via `FramebufferRotator`) into the buffer **not** being scanned out and issues a `DRM_IOCTL_MODE_PAGE_FLIP`, blocking on the flip-complete event (vsync throttle). Falls back to `SETCRTC` if the driver rejects page-flip. Still **software Skia** — the CR1102's Mali-400 GPU has lima/Mesa drivers but Avalonia GPU rendering is unverified; the i.MX 8M Nano has no usable GL, so Avalonia LinuxDrm's GL-backed `DrmOutput` is unavailable (this backend stays software Skia, tear-free via DUMB double-buffer + page-flip).
| `static class FramebufferRotator` | Pure, allocation-free pixel rotator (`Rotate(src, srcStride, dst, dstStride, dstW, dstH, bytesPerPixel, rotation)`). No Avalonia dependency, so host-testable with plain byte buffers; handles 4 bpp and 2 bpp, moving whole pixels (no format conversion or scaling). |
| `static class RotatingFramebufferPlatformExtensions` | `AppBuilder.StartLinuxFbDevRotated(args, rotation, fbdev?, scaling, inputBackend?, fps?)` — the rotated counterpart of the stock `StartLinuxFbDev`; constructs a `RotatingFbdevOutput` and hands it to `StartLinuxDirect`. `fps` (default 60) caps the render timer (`LinuxFramebufferPlatformOptions.Fps`); `fps <= 0` leaves the platform default. |
| `static class RotatingDrmPlatformExtensions` | `AppBuilder.StartLinuxDrmRotated(args, rotation, card?, scaling, inputBackend?, fps?)` — the DRM/KMS counterpart of `StartLinuxFbDevRotated`; constructs a `RotatingDrmOutput` and hands it to `StartLinuxDirect`. `fps` (default 60) caps the render timer (`LinuxFramebufferPlatformOptions.Fps`); `fps <= 0` leaves the platform default. |

The `Output` types are the display counterpart of the input backend: `FramebufferRotator` is pure BCL (host-testable like `CpuSampler`/`KeyGestureDetector`); `RotatingFbdevOutput` (single-buffered fbdev) and `RotatingDrmOutput` (tear-free DRM/KMS double-buffer) are the two output-backend wirings — same rotation model, same software-Skia rendering, different present path.

**Namespace**: `Cr1140.Avalonia.Display`

| Type | Role |
|------|------|
| `static class Backlight` | Thin, typed reader/writer for the display backlight under `/sys/class/backlight/` — the .NET counterpart of the Rust `cr1140-hal` `sys` backlight functions (`set_backlight` / `read_backlight` / `backlight_max` / `list_backlights`). `Default` (=`"backlight"`, the CR1140/CR1141 node name) and `MaxHint` (=400, the CR1140/CR1141 max) constants; `Set(name, value)` / `Read(name)` (raw `/sys/class/backlight/<name>/brightness`), `Max(name)` (reads `max_brightness`), `ListBacklights()`, plus `SetPercent(name, 0..100)` / `ReadPercent(name)` percentage helpers that scale against `max_brightness` so an app can offer a simple 0–100 % operator brightness control without knowing the panel's raw range. Writes return `bool` and reads return `uint?`/`double?` — every call degrades off-device (missing node / no permission) instead of throwing, like `ProcFs`. **Per-device:** CR1140/CR1141 node = `"backlight"`, max 400; CR1102 node = `"a00e0400.panel"`, max 255 `[live ✓ 2026-09-21]` — see `DeviceProfile.BacklightNode` / `BacklightMaxHint`. New internal `Root` property (filesystem prefix, default empty = `/sys/class/backlight`) lets the emulator redirect writes to a temp tree so backlight actuation is observable off-device.

The `Display` type is the screen-brightness counterpart of `LedSysfs`: pure BCL sysfs access (no Avalonia dependency), a deliberate mirror of the Rust `cr1140-hal` `sys` backlight primitives, degrading to a safe no-op off-device.

**Namespace**: `Cr1140.Avalonia.Leds`

| Type | Role |
|------|------|
| `enum Led` | The six onboard LED channels under `/sys/class/leds/` **for CR1140/CR1141**: the RGB **status** light (`StatusRed`/`StatusGreen`/`StatusBlue` = `*:status`, binary, `max == 1`) and the RGB **keypad button backlight** (`KbdRed`/`KbdGreen`/`KbdBlue` = `*:kbd_backlight`, 8-bit PWM, `max == 255`). Mirrors the Rust `cr1140-hal` `sys::Led`. **CR1102** has different LED hardware (two indicator LEDs `pri`/`sec`; keypad buttons backlit by D-Bus, not sysfs) — use the profile-driven `RgbLed` API. |
| `static class LedSysfs` | Thin, typed sysfs reader/writer — the .NET counterpart of the Rust `cr1140-hal` `sys` LED functions: `Name(Led)`, `Max(Led)`, `Set(name, value)` / `Read(name)` (raw `/sys/class/leds/<name>/brightness`), `SetTyped(Led, value)` (clamps to `Max`), `SetKbdBacklight(r, g, b)` (the three PWM channels as one RGB color), `ListLeds()`, plus **profile-driven**: `SetRgb(RgbLed, r, g, b)` / `ReadRgb(RgbLed)` (drives an arbitrary profile LED by its `RgbLed` descriptor; CR1102's pri/sec or CR1140's status/keypad). Writes return `bool` and reads return `uint?` — every call degrades off-device (missing node / no permission) instead of throwing, like `ProcFs`. New internal `Root` property (filesystem prefix, default empty = `/sys/class/leds`) lets the emulator redirect writes to a temp tree so LED actuation is observable off-device. |
| `enum LedMode` | Keypad-LED animation mode / brightness curve: `Solid`, `Dim` (50%), `Pulse` (2 s breathe), `Blink` (1 Hz), `Flash` (~4 Hz strobe), `Heartbeat` (double-beat, ~1.2 s). Mirrors the Rust `cr1140-sdk` `led::LedMode`. |
| `static class LedAnimation` | Pure animation math (no hardware, no Avalonia — host-testable like `FramebufferRotator`): `Name(LedMode)`, `Level(LedMode, t)` (brightness multiplier `0.0..=1.0` at `t` seconds), `Scale((r,g,b), level)` (scale a color by a level, rounding half away from zero). Mirrors the Rust `led::LedMode::name` / `level` / `scale`. |
| `sealed class LedDriver` | Drives an RGB LED from a base color + `LedMode`. Constructors: parameterless (drives the CR1140/CR1141 RGB keypad backlight via the legacy `Led` enum, backward-compatible) and `LedDriver(RgbLed)` (drives an arbitrary profile LED: CR1102's Primary/Secondary or CR1140's status/keypad). `SetColor((r,g,b))` / `SetMode(mode)`; call `Tick()` once per frame — it samples the mode's curve, scales the color, and writes the three sysfs channels **only when the value changes** (a steady color costs nothing after the first write). New drivers are off/`Solid`; no write until the first `Tick`. Mirrors the Rust `cr1140-sdk` `led::LedDriver`. |
| `sealed class IfmKeyboardLeds` | Drives the **CR1102's physical function-key + navigation-key (D-pad) backlights**, which are owned by the keyboard MCU over the `com.ifm.Keyboard` D-Bus interface (NOT sysfs — contrast the CR1140/CR1141 `*:kbd_backlight` LED). `SetAll(r,g,b)` (all keys, solid), `Reset()`, plus `LedIdList` / `Available`; invoked through the platform `gdbus` CLI on the system bus, fire-and-forget off the UI thread, and a no-op off-device (no `gdbus`/bus). Colors are **solid** — the MCU is a set-color surface, not a per-frame animation target (contrast `LedDriver`). The MCU exposes **12 backlight LEDs addressed by LED ID: F1–F8 = 0–7, the D-pad = 8–11** (valid range `[0,11]`). ⚠ **LED IDs ≠ evdev input key IDs** — the nav *input* keys are 11–15 but the nav *LEDs* are 8–11, so `IfmKeyboardLeds` drives `SetLedColor(0, [0..11], 0x00RRGGBB)`, **not** the input key IDs (reusing 11–15 aborts the call on the invalid 12–15 and leaves the D-pad dark). Confirmed on the live CR1102 `[live ✓ 2026-09-21]`. Consumed when `DeviceProfile.KeypadBacklightViaDbus` is true. |
| `sealed class KeypadBacklight` | **Device-agnostic keypad button backlight** — the entry point consumers use to drive "the keypad backlight" on any SKU. `KeypadBacklight.For(DeviceProfile)` resolves the transport: the sysfs `*:kbd_backlight` PWM LED via `LedDriver` on the CR1140/CR1141 (`SupportsAnimation`=true, honours `LedMode`), or the `com.ifm.Keyboard` D-Bus key backlights via `IfmKeyboardLeds` on the CR1102 (`SupportsAnimation`=false, solid). `SetColor((r,g,b))`, `SetMode(LedMode)` (ignored where solid), `Tick()` (pump the animation ~30 Hz; no-op on D-Bus), `Off()`/`Dispose()` (write 0 / `ResetLeds` so the MCU-owned CR1102 keys do not persist after teardown), plus `IsPresent`/`SupportsAnimation`. Fail-soft off-device like `LedSysfs`/`IfmKeyboardLeds`. |

The `Leds` types are the LED counterpart of the telemetry API — a deliberate mirror of the Rust `cr1140-hal` `sys` LED primitives (`LedSysfs`) and the `cr1140-sdk` `led` animation layer (`LedMode`/`LedAnimation`/`LedDriver`). `LedAnimation` is pure BCL (host-testable); `LedSysfs`/`LedDriver` are the sysfs wirings. The `Led` enum and legacy `SetKbdBacklight`/`SetTyped(Led)` API are CR1140/CR1141-specific; the profile-driven `SetRgb(RgbLed)` / `ReadRgb(RgbLed)` + `LedDriver(RgbLed)` API works across all devices. **Note:** the CR1102's keypad-button backlights are **not** sysfs LEDs — the sysfs `LedSysfs`/`LedDriver` API controls its two **indicator** LEDs (Primary/Secondary), while `IfmKeyboardLeds` drives the **physical key backlights** over the `com.ifm.Keyboard` D-Bus interface `[live ✓ 2026-09-21]`.

## Why this exists

Avalonia's built-in **LinuxFramebuffer input** (`Avalonia.LinuxFramebuffer.Input.LibInputBackend` and `EvDevBackend`) handles **touch and pointer input only** — no keyboard or keypad. The stock backends enumerate `/dev/input/event*` nodes and filter for devices with `INPUT_PROP_POINTER` or `INPUT_PROP_DIRECT`; a gpio-keys keypad (which sets neither) is silently skipped.

The CR1140/CR1141 is available as a **keypad-only SKU** (no touchscreen hardware), so a headless-framebuffer Avalonia app cannot receive input using the stock platform. This library provides the missing piece: a custom `IInputBackend` that directly polls the keypad evdev node and exposes a typed event.

The library targets **Avalonia 12.1.3** and **.NET 8.0** (matching the reference demo's platform).

## Conventions / decisions

- **Managed event pattern**: `EvdevKeypadInput` raises key events on background threads (the evdev reader thread for `KeyPressed`/`KeyReleased`; a gesture timer thread for `KeyTapped`/`KeyDoubleTapped`/`KeyHeld`/`KeyHolding`). The consuming app subscribes and marshals to the UI thread (`Dispatcher.UIThread.Post`). This is the **app-driven navigation pattern** — the app's view-model or FSM drives screen transitions and state changes in response to keys.
- **No Avalonia key injection**: The library does **not** inject Avalonia `KeyDown` events or manipulate focus. This is an intentional design decision to keep the input backend simple, explicit, and debuggable. Apps that need routed key events can extend `EvdevKeypadInput` to call `inputSink.Input(new RawKeyEventArgs(...))` in the `Initialize` method.
- **Evdev read loop**: The reader thread blocks on synchronous reads of `/dev/input/event*` (no `epoll`, no async I/O). Evdev nodes are character devices and block until an event is available; the synchronous read is simpler and sufficient for a single low-rate input source.
- **Down + up + gestures**: Key-down (`value 1`) raises `KeyPressed`; key-up (`value 0`) raises `KeyReleased`. Kernel auto-repeat (`value 2`) is **ignored** — holding is derived by the library's own timer so it works regardless of the gpio-keys autorepeat setting. On top of the raw down/up, a pure `KeyGestureDetector` derives `KeyTapped` (short press, no second tap in the window), `KeyDoubleTapped` (two taps within `DoubleTapWindow`), `KeyHeld` (one-shot when `HoldThreshold` is crossed), and `KeyHolding` (repeats every `HoldRepeatInterval` while held). Gesture logic is a separate, allocation-free, host-testable state machine (mirrors the pure `CpuSampler`/`ProcFs` ethos); `EvdevKeypadInput` owns the lock and the 25 ms tick timer that only runs while a key is active.
- **NuGet package**: `Cr1140.Avalonia` (PackageId), version `0.12.0`. Package README is this file (`PackageReadmeFile`); license is `GPL-3.0-only` (dual-licensed GPL-3.0-only OR commercial, same as the workspace).
- **Device profile is the single source of truth for per-device defaults**: `Cr1140.Avalonia.Devices.DeviceProfile` holds panel size (1280×800 for CR1102, 800×480 for CR1140/CR1141), touch/keypad presence, function-key/nav count, keypad device path/name (CR1102's uinput `"PDM3 virtual keyboard"` `[live ✓ 2026-09-21]`), touch device path/name (CR1102's `"/dev/input/event0"` / `"Atmel maXTouch Touchscreen"` `[live ✓ 2026-09-21]`), backlight node/max hint (CR1102 = `"a00e0400.panel"` / 255 `[live ✓ 2026-09-21]`), SoC thermal zone (null for CR1102 — no SoC thermal zone `[live ✓ 2026-09-21]`), and LED inventory (RgbLed list: CR1102 Primary/Secondary PWM LEDs `[live ✓ 2026-09-21]`; CR1140/CR1141 Status/Keypad LEDs). Emulator/input factories consume the profile (`EmulatorOptions.ForDevice(DeviceProfiles.Cr1102)`, `EvdevKeypadInput.ForDevice(DeviceProfiles.Cr1102)`) instead of hard-coding CR1140 constants. **Important:** these constants are **hints/defaults** — runtime reads remain authoritative (`Backlight.Max()` reads real `max_brightness` from sysfs, `SystemTelemetry` reads the real thermal zone, output backends read the real panel mode from fbdev/DRM). The profile documents and centralizes per-device defaults; it does not override runtime reads.
- **Desktop emulator (fast dev loop, off-device)**: Same app runs on device and desktop by depending on `IKeypadInput` instead of the concrete `EvdevKeypadInput`. The emulator redirects `LedSysfs`/`Backlight` sysfs roots to a seeded temp tree so LED/backlight writes from the real `LedSysfs`/`Backlight`/`LedDriver` code land in observable files and render live in the bezel window (status-LED dot, keypad-backlight tint, screen-dim overlay). The library stays dependency-clean — the `Emulator` namespace uses only core Avalonia; the consuming app supplies the windowing platform (`Avalonia.Desktop`). **Scope boundary**: the emulator emulates actuation surfaces (screen at panel resolution + backlight dimming, keypad, status LED, keypad backlight) and passes read-only telemetry (`SystemTelemetry`/`ProcFs`/`DeviceInfo`) through to the host — it is not fabricated, so off a macOS/Windows host telemetry shows `?`/nulls and on a Linux desktop host it shows host stats (intentional, honest readout).
- **Telemetry is data, not a control**: `SystemTelemetry` is a **pull-based, framework-agnostic collector** (no Avalonia dependency, no threads, no timers). The app owns the cadence — sample on a `DispatcherTimer` or whatever loop it likes — and every field is independently optional so a missing `/proc` node degrades to `null` rather than throwing. This is the .NET counterpart of the Rust `cr1140-sdk` `metrics::Telemetry`/`Snapshot` + `device` modules; the parsers in `ProcFs`/`DeviceInfo` are pure and unit-tested against the same fixtures.
- **Display rotation is an output backend, not a visual transform**: `RotatingFbdevOutput` rotates at the framebuffer boundary — Avalonia lays out and Skia renders at the **logical (rotated) size**, then the frame is rotate-blitted onto the panel. This keeps layout, hit-testing, and DPI correct for the orientation (no `RenderTransform`/`LayoutTransform` clipping games) and is the natural place to compensate for how the panel is physically mounted. The rotation math (`FramebufferRotator`) is pure and host-tested pixel-exact for all four angles (32/16 bpp, padded strides, round-trips); on-device, `none`/`90`/`270` each produce a distinct framebuffer. Unlike the keycode map, this is **not** CR1140-specific — it works for any single fbdev.
- **Two output backends, one rotation model, software Skia**: The package ships both `RotatingFbdevOutput` (single-buffered `/dev/fb0`) and `RotatingDrmOutput` (DRM/KMS DUMB double-buffer + page-flip on `/dev/dri/card0`). Both implement `IOutputBackend` + `IFramebufferPlatformSurface`, report the same **logical (rotated)** size, render with **software Skia** into a private back buffer, and reuse the pure `FramebufferRotator` for the rotate-blit — they differ only in the present path. DRM is the **tear-free** upgrade: Skia renders a full frame, it is rotate-blitted into the DUMB buffer **not** being scanned out, then a `DRM_IOCTL_MODE_PAGE_FLIP` presents it and the render thread blocks on the flip-complete event (which also vsync-throttles the loop). GL is deliberately **not** used — the i.MX 8M Nano has no working GL driver, so Avalonia's GL-based `DrmOutput` cannot render here; keeping Skia on the CPU is the whole point. If a driver rejects legacy page-flip, `RotatingDrmOutput` transparently falls back to a per-frame `SETCRTC` (tearing, but working).
- **LEDs mirror the Rust framework, split HAL/SDK**: The `Leds` namespace is a deliberate two-layer mirror. `LedSysfs` (+ the `Led` enum) is the HAL primitive — typed `/sys/class/leds/` reads/writes, one-to-one with `cr1140-hal` `sys` (`set_led`/`read_led`/`set_led_typed`/`set_kbd_backlight`/`list_leds`); it returns `bool`/`uint?` and degrades off-device instead of throwing, like `ProcFs`. `LedMode`/`LedAnimation`/`LedDriver` are the SDK animation layer, one-to-one with `cr1140-sdk` `led`: `LedAnimation` is pure, host-testable curve math (`Level`/`Scale`), and `LedDriver` holds a base color + mode and writes the three keypad-backlight channels **only when the computed value changes** (a steady color is free after the first `Tick`). Like telemetry, the LED types are offered as **primitives, not a control** — the app owns the tick cadence (a `DispatcherTimer`). The status LED is set per-channel via `SetTyped(Led.Status*, …)` (binary); the keypad backlight is one RGB color via `SetKbdBacklight`/`LedDriver`.
- **Backlight is a sysfs primitive, not a control**: The `Display` namespace's `Backlight` is a HAL-level mirror of the Rust `cr1140-hal` `sys` backlight functions — pure `/sys/class/backlight/` reads/writes (`Set`/`Read`/`Max`/`ListBacklights`), returning `bool`/`uint?` and degrading off-device instead of throwing, exactly like `LedSysfs`. On top of the raw counts it adds `SetPercent`/`ReadPercent` (0–100 % scaled against `max_brightness`) so an app can offer an operator brightness control without hard-coding the panel's range (400 on the CR1140). Like telemetry and LEDs, it is **data/primitive, not a control** — the app decides the UI, step size, and any safety floor (the demo keeps a 10 % minimum so a keypad-only panel can't be dimmed to an unreadable black).
- **Performance overlay design (pure-core + thin-wiring)**: Timing sourced at the output-backend present boundary — the backends call `FrameStatsRecorder.BeginRender()` / `BeginPresent()` / `EndFrame(vsync)` once per presented frame. `FrameStats` is the pure host-testable ring buffer (Fps/Mspf/Average/Best/Worst/Last for Total/Render/Present); `FrameStatsRecorder` is the thin clock+lock wiring; `PerfOverlay` is the non-interactive custom-drawn HUD `Control`. Render = Skia rasterize, Present = rotate-blit + page-flip/vsync wait, Total = present cadence, VSync = real DRM page-flip / fbdev `FBIO_WAITFORVSYNC` success. On software Skia (no GPU), the typical 'GPU' row is repurposed to Present. Backend instrumentation is opt-in (null recorder = no overhead). Retained-mode FPS honesty: Avalonia only redraws when something changes, so FPS is meaningful only while the overlay drives redraw (via `RedrawInterval` > 0); otherwise the panel idles and shows whatever the app's own activity produces.
- **Bounded page-flip wait (no idle freeze)**: `RotatingDrmOutput` presents by queuing a `DRM_IOCTL_MODE_PAGE_FLIP` with `PAGE_FLIP_EVENT` and waiting for the flip-complete event — but the wait is `poll()`-bounded (~250 ms) and parses the DRM event stream to consume only `DRM_EVENT_FLIP_COMPLETE`, never an unbounded `read()`. If the i.MX LCDIF drops a vblank/flip event (observed after long idle — the render loop free-runs, so it flips ~60×/s and eventually loses one), the render thread proceeds instead of blocking forever (which previously **froze the panel until the next keypress woke a fresh flip**); and a flip `EBUSY` drains any stale event and retries once, so a single missed event can't permanently drop the loop to tearing modeset presents. `ContainsFlipComplete(ReadOnlySpan<byte>)` is pure/host-testable.
- **Fixed-FPS render cap (CPU headroom knob)**: `StartLinuxDrmRotated` / `StartLinuxFbDevRotated` take an optional `fps` (default 60) that sets Avalonia's `LinuxFramebufferPlatformOptions.Fps` — the `DefaultRenderTimer` interval (`1/fps`) that paces the compositor's render+present. Rendering is **software Skia** (no GPU on the i.MX 8M Nano) and the DRM/fbdev present does a **full-frame rotate-blit** (~1.5 MB) + page-flip on **every** present regardless of dirty region, so present CPU is proportional to the present rate. Measured on-device (CR1140, 2×A53, DRM, 25 s settle / 20 s window): **steady-idle CPU is ~5 % of one core and fps-independent** (Avalonia is retained-mode — an idle screen produces no commits, so nothing is presented and the cap is a no-op); **under continuous redraw CPU scales with fps** — ~68 % @60, ~48 % @24, ~31 % @15 of one core — so capping 60→24 reclaims ~20 pp (~10 % of the 2-core SoC) and 60→15 ~54 %. Net: the cap frees CPU **only while the panel is actively re-rendering** (animations, live gauges, scrolling, or the intermittent DRM free-run flip state), not at idle; 24 is a sensible operator-panel default (smooth enough, real headroom under load, zero idle penalty). `fps <= 0` leaves the Avalonia default (60). The demo wires it via `--fps=` / `CR1140_FPS`.
- **systemd watchdog (CODESYS liveness, without CODESYS)**: `SystemdWatchdog` (namespace `Cr1140.Avalonia.Systemd`) is a dependency-free `sd_notify(3)` client that mirrors how the stock `codesys.service` supervises liveness (`Type=notify` + `WatchdogSec=`). `Start()` (call on the UI thread) sends `READY=1`, then pings `WATCHDOG=1` on a `DispatcherTimer` at half of `WATCHDOG_USEC` — driven on the **Avalonia UI thread**, so a wedged render/UI thread stops the pings and systemd trips the watchdog (a background-thread ping would keep firing through a frozen UI and hide the hang). It reads `NOTIFY_SOCKET`/`WATCHDOG_USEC` from the environment, writes the AF_UNIX datagram protocol directly (no `libsystemd` dependency), and **no-ops when `NOTIFY_SOCKET` is absent** (desktop/dev), so it is safe to construct + `Start()` unconditionally. The demo wires it from `App.OnFrameworkInitializationCompleted`; its unit is `Type=notify`/`WatchdogSec=30s` with **restart-in-place** (`StartLimitBurst=5/60s`, not CODESYS's `reboot-force`), and `install.sh` arms the imx2-wdt **hardware** watchdog via a `RuntimeWatchdogSec=60` `system.conf` drop-in as a backstop if systemd itself hangs (removed by `restore.sh`).

## Caveats

### Keycode map is CR1140-specific

The evdev keycode → `KeypadKey` mapping is **hard-coded for the CR1140/CR1141 gpio-keys layout**. If the device's keypad layout changes (different evdev codes, additional keys, or a different key count), the enum and mapping table must be updated. The library does **not** auto-detect or configure the keycode map at runtime.

### Requires `/dev/input/event1` read access

The process must have **read permission** on the evdev device node. On the CR1140/CR1141, the keypad is `/dev/input/event1`, owned by `root:input`, mode `0660`. Run the app as root or add the user to the `input` group (`usermod -aG input <user>`).

### LinuxFramebuffer or LinuxDrm platform only

This backend is only compatible with Avalonia's **LinuxFramebuffer** (`StartLinuxFbDev`) or **LinuxDrm** (`StartLinuxDrm`) platforms. It does **not** work with X11, Wayland, or desktop platforms — the `IInputBackend` interface is specific to the headless-framebuffer code path.

### Display rotation does not transform pointer/touch input

`RotatingFbdevOutput` / `RotatingDrmOutput` rotate the **rendered output** only. Pointer/touch coordinates from Avalonia's stock LinuxFramebuffer input backends are delivered in **physical** framebuffer space and are **not** rotated to match, so a rotated UI driven by touch would have mismatched coordinates. This is fine for the keypad-only SKU this package targets (`EvdevKeypadInput` keys carry no screen coordinates), but a touch SKU using rotation would need a coordinate transform in the input path. `RenderDirectlyToMappedMemory` is not applicable — a private back buffer is always used because the frame must be rotated (and, for DRM, page-flipped) before it reaches the panel.

### DRM output needs `/dev/dri/card0` + master (exclusive display)

`RotatingDrmOutput` opens the DRM primary node (default `/dev/dri/card0`), becomes **DRM master**, and modesets the panel. Only one process can be DRM master at a time, so — exactly like the fbdev path — the app must own the display exclusively: mask `app-launcher`/`ifm-local-setup`, CODESYS, and any other display client first (see `deploy/install.sh`). It presents at **32 bpp XRGB8888** (`Bgra8888`), matching the CR1140/CR1141 panel; there is no 16 bpp path. It picks the **first connected connector** and its preferred mode — sufficient for the single-panel device, not a general multi-head selector. Off-device (no DRM node) the ctor throws — the demo makes DRM the **default** and catches this to fall back to `RotatingFbdevOutput` (opt out entirely with `--fbdev` / `CR1140_OUTPUT=fbdev`).

### No error recovery on device disconnect

If the evdev device node is removed (USB keypad unplugged, driver unloaded), the reader thread will throw an `IOException` and terminate. The exception is **not** caught; the app will see the `KeyPressed` event stream stop. A production implementation might add a reconnection loop or raise a `DeviceDisconnected` event.

### Telemetry reads Linux `/proc` + sysfs (null off-device)

`SystemTelemetry`, `ProcFs`, and `DeviceInfo` read Linux `/proc`, `/sys/class/thermal`, `/sys/class/hwmon`, and `/sys/class/net`. On a non-Linux host (or when a node is absent) every reader degrades to `null` (`"?"` for the string helpers) instead of throwing — safe to reference from cross-platform tooling, but it means **all fields being `null` is indistinguishable from "not on the device."** The SoC thermal zone and the `hwmon0` board sensor are CR1140-specific; pass a different zone to the `SystemTelemetry(uint)` ctor for other hardware.

### LED writes need `/sys/class/leds` write access (silent no-op off-device)

`LedSysfs`/`LedDriver` write the `brightness` node under `/sys/class/leds/<name>/`. On the CR1140/CR1141 these are owned by `root` (mode `0644`), so the app must run as root or a udev rule must grant its group write access. Off-device (or without permission) every write returns `false` and reads/`ListLeds()` return `null` instead of throwing — safe to reference cross-platform, but a `false` from `LedDriver.Tick()` means the color was **not** applied (and is not cached, so the next `Tick` retries). The LED leaf names (`*:status`, `*:kbd_backlight`) are CR1140/CR1141-specific.

### Backlight writes need `/sys/class/backlight` write access (silent no-op off-device)

`Backlight.Set`/`SetPercent` write the `brightness` node under `/sys/class/backlight/<name>/`. On the CR1140/CR1141 the node is `backlight` (owned by `root`), so the app must run as root or a udev rule must grant its group write access. Off-device (or without permission) every write returns `false` and reads (`Read`/`Max`/`ReadPercent`/`ListBacklights`) return `null` instead of throwing — safe to reference cross-platform, but a `false` means the brightness was **not** applied. `SetPercent`/`ReadPercent` need a readable `max_brightness` (400 on the CR1140); if it can't be read they degrade to `false`/`null`. The backlight node name is CR1140/CR1141-specific. Beware: writing `0` turns the backlight fully off — on a keypad-only panel there is no touch to recover, so an operator UI should keep a non-zero floor (the demo uses 10 %).

### Performance overlay self-perturbation and requires TopLevel OverlayLayer

The `PerfOverlay` HUD **self-perturbs** the frame time it measures — drawing the overlay itself consumes CPU and elongates the frame. This is inherent to any on-panel diagnostics HUD and is kept light (the overlay is custom-drawn and text-only; no heavy controls). FPS is meaningful **only while the overlay is driving redraw** (via `RedrawInterval` > 0 in `PerfOverlayOptions`); Avalonia is **retained-mode** — the UI only redraws when something changes, so without the overlay's own redraw driver the panel idles and shows whatever FPS the app's own activity produces. `AttachPerfOverlay` requires a `TopLevel` with an `OverlayLayer` (the standard `Window` and embedded `TopLevel` both provide one).

### Emulator telemetry not fabricated (host pass-through), needs Avalonia.Desktop

The desktop emulator emulates actuation surfaces only — screen (at panel resolution + backlight dimming), keypad, status LED, and keypad backlight. Read-only **system telemetry** (`SystemTelemetry`/`ProcFs`/`DeviceInfo`) is deliberately **not** emulated — it passes through to the host, so off a macOS/Windows host the Telemetry screen shows `?`/nulls (no `/proc`, no thermal zones) and on a Linux desktop host it shows **host** stats (not fabricated device values). This is intentional — an honest readout of what the library actually reads. `EmulatedDevice` is **single-instance** (the `LedSysfs.Root` / `Backlight.Root` hooks are shared statics; creating a second instance is not supported). The emulator uses only core Avalonia — the consuming app must supply the windowing platform (add `Avalonia.Desktop` to the app's project and call `UsePlatformDetect()` + `StartWithClassicDesktopLifetime()`).
